## Statement
When delivering a finalized block to the application, the replica shall have completed durable
storage of that block.

## Rationale
Applications change their own state based on delivered blocks and, after a restart, read back the
last block they processed. A block delivered before it was durable could be lost in a crash while
the application keeps state derived from it, and that read on restart would fail.

## Evidence
`consensus/src/marshal/mod.rs:153-155@55cd57fd2137`: marshal only emits a block after it has
durably persisted it, so that applications that make stateful changes based on a block can access
the same block on restart, where startup logic often reads the last processed block infallibly.
`consensus/src/marshal/mod.rs:140-142@55cd57fd2137`: a finalized tip can be reported before the
block and finalization archives complete a durable sync, applications must not use it as a
durability signal, and block delivery provides that guarantee. The actor's dispatch
documentation states the same barrier: buffered archive writes are readable before they are
durable, so blocks are only sent once the finalized archives are durable.

## Preconditions / assumptions
Finalized-tip notifications are not deliveries. A storage failure is fatal to the replica and is
not a violation.

## Observation hints
A delivery is the `Update::Block` report in `Actor::try_dispatch_blocks`
(`consensus/src/marshal/core/actor.rs`); past that call the block is with the application.
Finalized-archive writes are made durable by `Actor::sync_finalized` and the pooled
`Actor::start_finalized_sync`, and `DispatchGate` (`consensus/src/marshal/core/durability.rs`)
tracks the writes no completed sync covers yet. A ghost set of heights whose archive write a
completed sync covered, updated where each sync completes, decides the check at the report. A
floor anchor is stored and synced in `Actor::apply_pending_floor` before dispatch resumes.
