## Statement
When the replica, while certifying a notarized proposal, skips requesting the proposal's block
from peers because it finds the block locally, the replica shall at that moment hold the block in
storage that peer traffic cannot evict, or have already delivered the block to, or registered a
wait for it on behalf of, that certification or the verification the certification waits on.

## Rationale
A Byzantine leader can form a notarization after sending its block to only f+1 honest replicas.
The honest replicas left without the block can certify only through certification's round-bound
fetch. If a local lookup cancels that fetch while the block sits only in a cache that peer traffic
can evict, and no waiting verification owns it yet, the block can disappear with no fetch
outstanding, and certification never completes. Simplex needs every honest replica to certify a
notarized proposal eventually: one stuck honest replica, with the Byzantine replicas withholding
votes, can leave every finalize and nullify set below quorum. A transient observation of the block
must not end recovery before ownership passes to the verifier.

## Evidence
PR #4606 fixed this attack at n=4, f=1: Byzantine leader B sends block X only to honest H0 and H1,
which form the notarization with B, then sends honest V (the next leader) the notarization without
X and briefly places X in V's buffered broadcast cache through its own connection. V's
certification sent `HintNotarized` before verification registered its `DigestFallback::Wait`
subscription, so the hint found X in the cache and skipped the fetch without persisting X. Further
same-peer traffic from B evicted X before the wait was registered. V never certified or entered the
next view while H0 and H1 advanced, and with B withholding votes finality halted indefinitely. The
fix registers the verifier's wait before publishing the certification gate in `Inline` and
`Deferred` verification.

## Preconditions / assumptions
Storage that peer traffic cannot evict means marshal's verified and notarized block caches and its
finalized archive and, in coding mode, the shards engine's cache of reconstructed blocks, which only
durable progress retires. The standard buffered broadcast cache, bounded per peer, does not count.
A wait counts as registered once marshal's core has handled the subscription for the block, whether
it answered at once or queued it; a queued wait is answered when the block reaches the cache. When
a verification ends without a result, certification falls back to its own round-bound
subscription, and the statement applies again at that moment. Rounds already covered by a
finalization, where certification no longer matters, are excluded.

## Observation hints
The skip happens in the `Message::HintNotarized` arm of `consensus/src/marshal/core/actor.rs`, when
`find_block_by_commitment` returns a block and `fetch_if_permitted(resolver,
Request::notarized(round))` is not called. `handle_subscribe` with `CommitmentFallback::FetchByRound`
answers a local hit directly, which satisfies the statement by construction. For the storage part,
call `find_block_in_storage_by_commitment` separately, because the combined lookup checks the
buffer first. In coding mode the buffer is the shards engine
(`consensus/src/marshal/coding/shards/engine.rs`), whose lookup returns only reconstructed blocks,
so a buffer hit there is already secured. For the wait part, a ghost set of the digests or
commitments for which `handle_subscribe` has run (answered, or inserted by
`subscriptions.rs::insert`) is enough; clear a replica's entries when it restarts, because its
subscriptions do not survive. The ordering the fix relies on is `subscribe_by_digest(digest,
DigestFallback::Wait)` before `gates.insert` in `Inline::verify` (`standard/inline.rs`) and
`Deferred::verify` (`standard/deferred.rs`), `certify` taking the gate before sending
`hint_notarized`, and the core mailbox draining these messages in FIFO order (`core/mailbox.rs`,
test `policy_drains_fifo`). In coding mode `certify_from_existing_task` (`coding/marshaled.rs`)
calls `shards.notarized` before `hint_notarized`, while `deferred_verify` subscribes inside its
spawned task. A check does not need the eviction: the pre-fix ordering already violates the
statement when the hint finds the block in the buffered cache before the verifier's wait was
handled. Regression tests: `test_standard_certify_retains_transient_buffer_hit_through_eviction`
(`standard/mod.rs`) and `test_late_subscription_uses_notarized_cache_after_peer_buffer_pressure`
(shards engine).
