## Statement
When the replica's certification of a proposal `c` has returned failure, the replica shall not
propose a container whose parent is `c` and shall not sign a notarize vote for a proposal whose
parent is `c`, unless it holds a finalization of `c` or of a descendant of `c`.

## Rationale
A failed certification means the application judged `c` unfit to extend. The protocol tolerates
`c` being notarized, but relies on honest replicas refusing to build on it, so that `c` is either
skipped by a nullification or never extended. A replica that loses the rejection (after a restart,
pruning, a replacement notarization, or an optimistic child verified before the result arrived)
would extend a chain the application rejected. A finalization overrides the local verdict because
it proves a quorum certified `c`.

## Evidence
"If `certify` returns `false`, the participant broadcasts `nullify` for the view instead (treating
it as an immediate timeout), and will refuse to build upon the proposal or notarize proposals that
build upon it" (Certification). "Only move to view `v+1` and broadcast `finalize(c,v)` if
certification succeeds, otherwise broadcast `nullify(v)` and refuse to build upon `c`" (Deviations
from Simplex Consensus).

## Preconditions / assumptions
Certification is deterministic, so honest replicas agree on the result; this invariant concerns
only the replica's own result. A result restored from the journal after a restart counts. Votes
replayed from the journal after a restart are not new signatures.

## Observation hints
Certification results arrive through `State::certified(view, is_success)` in
`consensus/src/simplex/actors/voter/state.rs`. Notarize votes are signed in
`State::construct_notarize`. Proposing is split: `State::try_propose` (through
`Round::propose_ready`) picks the parent and asks the application to build on it, and the
proposal only leaves the replica later, when `Actor::process_proposed` in
`consensus/src/simplex/actors/voter/actor.rs` records it with `State::proposed` and relays
`Plan::Propose`. The replica handles certification results while that build is outstanding, so
the parent can be rejected between the two, and the relay is where the container leaves the
replica. The payload relay is not a consensus message and a restarted proposer may relay a
different payload for the same round, so a check there is about the parent the container
builds on, never about the payload. The existing tests `failed_certification_blocks_optimistic_child_notarize`
and `replayed_failed_ancestor_blocks_direct_descendant_until_finalization` show the intended
behavior. A check should keep a ghost set of rejected proposals (view and digest) and assert at
the relay of a local proposal and at each notarize signature; at the signature, note that the
implementation's own optimistic-ancestry guard can return before a check placed late in
`State::construct_notarize` is reached.
