## Statement
While the replica, before a crash, held the leader's proposal a of view v with its verification
still pending, then received a notarization of a different proposal b of v, recorded the leader's
equivocation, blocked the leader and signed no vote for v, the replica, restarted from its journal
and back in view v, holds b as its proposal for v with no equivocation recorded and is certifying
b again.

## Rationale
The protocol tells a replica that certifies the notarized proposal of v to skip its finalize vote
when it has "observed l equivocate in v". The implementation answers that question from one place
only: the in-memory proposal slot of the view. The slot is not journaled, because the journal holds
the replica's own votes, the certificates it verified and its certification results, and raw votes
from peers are neither journaled nor rebroadcast. A replica that detects the equivocation from a
certificate, as here, where the leader's vote for a reached it as a proposal and the notarization
of b then displaced a, has signed nothing for v, so after the crash its journal holds the
notarization of b and no trace of a. On replay the restored notarization lands in an empty slot,
is recorded as a new unverified proposal, returns no equivocator, blocks nobody and re-enters the
certification candidates, so the first pass of the main loop dispatches certification of b again.
That is the target state: the replica is one certify verdict away from a decision whose
precondition it has forgotten.

The continuation is fixed by the code. The restored slot has not asked for verification in this
incarnation, so the replica verifies b and, once b's block reaches its fresh application, signs a
late notarize vote for b; when the certification passes it enters v+1 and signs finalize(b, v),
because its same-term nullify gate is empty, b's parent is explicit, and the slot is unequivocated.
That finalize vote breaks the letter of INV-0014, which forbids a finalize vote after an
equivocation "observed through votes or certificates" and exempts restored certification results
but says nothing about a restart erasing an observed equivocation; the unit test that restores a
conflict after a restart does so only from the replica's own journaled notarize vote, which this
replica never cast. Agreement is not at stake with four participants and one faulty, since two
notarizations of one view cannot form, so the payoff is a spec-versus-implementation gap on a
stated rule plus a loss of the externalized fault proof: after the restart no replica blocks the
equivocator, and only the retained reporter of the restarted replica holds the leader's vote for
a next to the leader's signature in the notarization of b.

Reaching the state is rare for random fuzzing but cheap for a scaffold: the harness, as the
Byzantine leader, splits its notarize votes as the Equivocator mock does and never relays a's
block, so the mock application parks a's verification forever; it crashes the replica inside the
mock certify latency and restarts it on the same partition with its retained reporter. The
campaign cannot see the outcome today: the INV-0014 probe keeps its per-view equivocation flag in
the per-incarnation voter state, so it shares the implementation's amnesia, and the fuzz oracle
for vote equivocation excludes the Byzantine participant's signatures by index. The retained
reporter and the network oracle's list of blocked pairs are the only state that survives the
restart and can carry the pre-crash equivocation to a check.

    pub fn construct_finalize(&mut self, view: View) -> Option<Finalize<S, D>> {
        // We don't need to finalize views that are already finalized.
        if view <= self.last_finalized {
            return None;
        }

        // Certificates can create rounds arbitrarily far ahead. Do not vote
        // until the view is admissible under this node's lookahead policy.
        if !self.admits_outbound(view) {
            return None;
        }

        // Blocked by a same-term nullify vote unless an observed finalization
        // covers it (proving that nullification can never form). The plain
        // comparison suffices for coverage: the nullify vote is at or above
        // term_start(view) and last_finalized < view, so a finalization at or
        // above the nullify vote necessarily lies in the same term.
        if let Some(nullified) = self
            .highest_local_nullify_in_term(view)
            .filter(|nullified| *nullified > self.last_finalized)
        {
            debug!(%view, %nullified, "withholding finalize vote due to same-term nullify");
            return None;
        }

        // Optimistic notarize votes can notarize a child ahead of its parent's
        // certification, and finalization must not run ahead of that anchor.
        // Certification already applies this, so it only matters when replay
        // restores a certified round without re-running that precheck.
        if !self.explicit_parent_ready(view) {
            return None;
        }
        let candidate = self.views.get_mut(&view)?.construct_finalize()?.clone();

        // Signing can only fail if we are a verifier, so we don't need to worry about
        // unwinding our broadcast toggle.
        Finalize::sign(&self.scheme, candidate)
