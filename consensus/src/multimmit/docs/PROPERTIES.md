# Multimmit properties and evidence

This ledger ties each in-scope consensus property to one production owner and to review evidence.
[`STATE_MACHINE.md`](STATE_MACHINE.md) defines the implementation transition system. The
[Multimmit draft, arXiv:2607.21021v2](https://arxiv.org/html/2607.21021v2) defines protocol semantics.
The paper's Section 4.2 definitions say that a V-QC contains exactly `n - f` messages and that
`ProposeChains` sends the referenced V-QC whether or not it was forwarded before. The author's
subsequent amendment permits two implementation choices used here: a proposal need not retransmit
the exact same parent V-QC if that exact certificate was already forwarded, but it must transmit a
distinct selected same-view V-QC; and an implementation may retain `n - f..=n` complete attributed
messages in a V-QC. This file is a permanent review index, not a second executable model and not a
specification separate from the production marshal.

A property is covered only when the named owner is its sole mutator and the evidence appropriate to
the claim is present. The property table states the obligations; the executable evidence index below
names current tests for mechanisms that can be exercised.

Evidence is classified as follows:

- **Executable test:** a finite, deterministic scenario or matrix that executes the named production
  mechanism. It is regression evidence, not a proof of a universally quantified paper result.
- **Static/code inspection:** a type, owner, call graph, or absence claim checked against the current
  tree. This is the only honest evidence for boundaries such as "consensus has no dense delivery
  cursor," "Catalog is the sole archive owner," or "certificates never enter `Automaton`."
- **Environment/liveness assumption:** a condition supplied by the paper's model or the attached
  application/runtime, not something an in-process test can establish. Tests may exercise a schedule
  satisfying the condition but cannot prove that the environment eventually supplies it.

Protocol liveness and catch-up obligations assume at most `f` faulty participants in total. A
crashed, paused, or otherwise unavailable participant consumes that fault budget just like an
actively Byzantine participant. Executions with more than `f` faulty participants must remain
bounded and fail closed, but they do not justify extra recovery witnesses, protocol branches, or
retained state intended to restore progress after the paper's fault assumption has already failed.

The paper's abstract set `S` retains every received vote indefinitely. A bounded implementation
cannot do that through arbitrarily many pre-GST views: one Byzantine signer can keep an unbounded
number of old pools one equivocation short of finality. Multimmit retires unfinished pools with the
view window and never blocks view progress on their capacity. P-LEAD-1 applies to retained pools;
post-GST liveness comes from the ordinary correct-leader view and its covering L-QC.

## Marshal ordering and delivery

Marshal owns authenticated history acquisition, complete transaction-block retrieval, the paper's recursive
`Ord`/`Emit` transition, settled/unsettled sweeps, exact-block duplicate reconciliation, and its
durable delivery cursor. Application bodies remain opaque, so transaction-level duplicate semantics
remain application-owned. Consensus and marshal meet only at the best-effort authenticated activity
stream described by P-MATTACH-1.

`Automaton::verify(context, payload_digest)` is exclusively the application validity and availability
fence for the named producer payload and parent. Static inspection must continue to show that V-QCs,
nullifications, L-QCs, and leader blocks go through consensus verification and Resolver instead. An
executable application test can show the fence delaying or releasing authority; it cannot turn
`Automaton` into a certificate-fetch path or establish eventual external availability.

## Executable completeness

The property table and executable evidence index are the permanent review checklist. An executable
mechanism is not covered unless the indexed layers exercise it. Static boundaries and environment
assumptions are reviewed under their own evidence class rather than represented by a convenient but
unrelated test name. Renaming or moving a test requires updating its exact path here. Semantic truth
comes from the invariant assertions and scenarios themselves, not from the presence of a name.
