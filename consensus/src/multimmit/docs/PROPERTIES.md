# Multimmit properties and evidence

This document is for readers checking the implementation against the
[Multimmit specification](https://arxiv.org/abs/2607.21021v5) (arXiv 2607.21021, version 5). It lists
where the code departs from the paper, the properties the code must keep, the tests and fuzz
campaigns that exercise each property, and what that evidence leaves out.
[`STATE_MACHINE.md`](https://github.com/commonwarexyz/monorepo/blob/main/consensus/src/multimmit/docs/STATE_MACHINE.md)
describes the state, transitions, and invariants behind these properties, and its
[Terminology](https://github.com/commonwarexyz/monorepo/blob/main/consensus/src/multimmit/docs/STATE_MACHINE.md#terminology)
section defines the terms used here.

## Assumptions and evidence

Liveness assumes that at most `f` participants are faulty, crashed, or unavailable in total, that
messages between correct participants arrive after GST, that the runtime and storage keep working,
and that the application eventually takes custody of every block from a correct producer. Outside
those assumptions the implementation must stay bounded and fail closed, but it need not make
progress.

The evidence cited here comes in four kinds:

- **Tests** run a fixed, deterministic scenario or matrix through the production code. They catch
  regressions. They do not prove a protocol claim in general.
- **Fuzz campaigns** let input bytes choose protocol actions, topology, failures, or artifacts.
  Saved inputs reproduce failures and mutation widens the schedules covered, but a campaign is still
  not a proof.
- **Code inspection** covers claims about types, ownership, call graphs, or the absence of
  something: for example, that consensus keeps no dense delivery cursor, that marshal's owner is the
  only store mutator, or that certificates never reach `Automaton`.
- **Environment assumptions** are conditions that the model, the application, or the runtime must
  supply. A test can run a schedule that satisfies one, but it cannot show that the environment
  always will.

## Deviations from the specification

These are the places where the implementation departs from the paper or leaves out one of its
optional features. The [crosswalk](#specification-crosswalk) below maps every section, lemma, and
theorem.

| Specification item | Implementation | Consequence |
|---|---|---|
| Section 4.1, Algorithm 1, DA votes | A validator DA-votes for a block only after `Automaton::verify` returns `true` for it. The paper DA-votes every eligible block with no application check. | The paper's liveness proof assumes its own rule, so liveness here also assumes that every block from a correct producer eventually verifies at every correct validator (P-AUTO-1, P-LIVE-1). |
| Section 4.2, Algorithm 2, `ProposeChains` | The leader proposes each chain at its highest held DA certificate. Newer blocks reach voters as vote extensions, at most `e` per chain. | Proposal validity still admits up to `d` blocks per chain, so voters accept a leader that follows the paper (P-PIPE-1, P-VQC-1). |
| Section 4.2, pool settledness | Core uses `max_child_support + (n - \|P\|) <= f` in place of the paper's `beta + (n - \|P\|) <= f`. | The rule is more permissive when votes beyond the tip split across incompatible branches. [Leader finality](https://github.com/commonwarexyz/monorepo/blob/main/consensus/src/multimmit/docs/STATE_MACHINE.md#leader-finality) explains why it stays safe (P-TIPS-1). |
| Section 4.2, retained pool set `S` | An unfinished pool retires with its bounded view window. | A late vote from before GST can cost a local finality opportunity. Within the fault bound, a covering L-QC restores finality (P-RET-1, P-LEAD-1). |
| Section 6, backup proposals | Not implemented. | Timeout and nullification recover from a crashed leader. |
| Section 6, ordering by reputation | Not implemented. | Marshal keeps the fixed horizontal chain order, with no blame set or per-view shuffle. |
| Section 6, one signature scheme | Not implemented. | Each key role is its own scheme, chosen by the deployment's suite (the `scheme::Scheme` trait). In the default BLS12-381 suite, DA certificates and nullifications use threshold BLS signatures, and votes, novotes, blocks, and V-QC/L-QC transcripts use BLS multi-signatures aggregated over their distinct messages. The opt-in synchronized aggregate suite verifies a certificate with one pairing product however many distinct votes it covers, and the Ed25519 suite lists signatures. |
| Section 6, transport suggestions | Content-addressed vote transport and advertise-and-pull forwarding are not implemented. | Votes and certificates travel as complete messages. Batch verification, from the same section, is implemented. |
| Theorem 4, generalized threshold | Not implemented. | The extension threshold is `n - f`. |
| Not in the specification: portable proofs | Consensus reports each verified L-QC with the finality it proves on its own and the history records placed since its last report, and marshal orders its output only from durable L-QCs and records. A direct finality result fixes placement but never authorizes delivery. | Delivery trails local finality by the L-QC's arrival, and a block that only a direct result settles waits for a later L-QC that proves it. Any node can rebuild the order from stored proofs and serve them (P-MATTACH-1, P-MSYNC-1). |
| Not in the specification: certificate identifiers | A V-QC or L-QC is identified by its artifact identifier, a kind-separated hash of its canonical encoding. Leader blocks name their parent V-QC by it. | The engine hashes each received certificate once (P-ADM-1). |
| Not in the specification: binding receipts | Each chain has its own `d` and `e`, and the DA quorum may be raised from `n - 2f` to `n - f`. A chain with `d = 0` places only certified blocks: proposals carry no blocks above its certified base, its producer and validators work within its pipeline window (`d_DA`, one by default and configurable wider) above the certified anchor, and a rotating set of `f + 1` validators per view forward a certificate that stays unplaced for a full view to the next leader. On a receipt chain (`d = 0` and `e = 0` under the `n - f` quorum) every validator sends its DA vote to every other validator and recovers the certificate itself. | A receipt chain's DA certificate is a binding receipt once any correct validator holds it, and a correct producer's certificate reaches every correct validator without the producer. An equivocating producer can withhold a certificate it completed with its own share, so a client holding a receipt must deliver it to a correct validator. The `n - f` quorum is epoch-wide, so pipelined chains need it too. Receipt chains cost `n^2` DA-vote messages per block on that chain, and certificate recovery at every validator rather than only its producer. Other chains keep the producer-only route. Forwarding is best effort and outside the durable outbox (P-PIPE-1, P-DA-1). |

## Properties

Each property names the component that owns it and the durable record that witnesses it. The
[evidence index](#evidence-index) lists the tests for each ID.

| ID | Property | Owner | Durable witness |
|---|---|---|---|
| P-ADM-1 | Hostile input, including bytes read back during recovery, cannot use unbounded memory, crash the process, poison a later valid artifact, or get a transport peer quarantined without objective evidence. Rejecting input grants no authority. | Ingress, verifier, Core admission, bounded storage readers | Only admitted events are recorded. Input enters through observation, verification completion, dependency resolution, or recovery decode. |
| P-OBS-1 | Sticky selections and transcripts follow the order in which artifacts were observed, whatever order the workers finish verifying them in. | Core admission, view, and finality | Observation assigns each artifact an identity, a verdict admits the artifact against that identity, and the selected transcript is recorded as an event. |
| P-OWNER-1 | Core is the only owner of durable protocol state and authority. The voter feeds Core typed inputs and runs the capabilities Core returns. Chain planes hold volatile block copies, application jobs, and derived eligibility, but only Core reserves a DA choice or advances a certified frontier. Producer inputs stay separate from view and leader inputs. | Voter, chain planes, `CoreState` and `Machine` | `Input` variants, generation-scoped `ValidatorCommand`s and `DaVotesOffer`s, and ordered `DomainEvent`s. |
| P-SIGN-1 | A validator signs at most one subject per protocol signing slot, across crashes. Each signing slot maps to one signature period (one vote or novote per view, one leader block per view, one header per height), so with a synchronized aggregate suite this also keeps every ordinary key unforgeable. | Core durability and signing slots | The reservation event, made durable before the signature is exposed and replayed on recovery. |
| P-ACCT-1 | Two conflicting authenticated claims prove producer, leader, vote, vote/novote, or DA-vote equivocation. When both claims are held in bounded live evidence, Core quarantines the signer and never an honest relay that carried the evidence. Omission, timeouts, application rejection, and other suspicions that cannot be proven to others never trigger quarantine. | Protocol types and signature scheme, Core accountability index, voter blocking path | None. Evidence comes from verified artifacts or certificate transcripts and lives in a bounded volatile index. |
| P-EXP-1 | Nothing created locally that carries authority is exposed until the journal range covering it is durable. Each reducer poll emits at most one contiguous journal range and runs only when a journal command slot is free. | Core durability acknowledgement, journal owner | The staged cursor range, the single journal command slot, and the acknowledged cursor, with an explicit release outcome. |
| P-REP-1 | Recovering from a durable prefix gives the same state as running without interruption up to that prefix. | Core durability, snapshot and event reducer | A version-0 snapshot at the acknowledged cursor plus the contiguous journal suffix. |
| P-PUB-1 | A publication is persisted before it is sent, is idempotent across crashes, and is retired only by its semantic successor. Exit proofs for different views may become ready in any order, and their live obligations share the durable outbox limit instead of a separate per-view certificate count. | Core publication, Egress | A stable effect ID, a typed durable obligation, and a typed successor event. |
| P-BND-1 | Every queue, job, retained object, publication turn, and disk suffix has a validated finite limit. A derived mirror has the same limit as the state it mirrors and cannot reject work its owner already admitted. | Resource profile, Core service metadata and retention, collaborator permits | Service metadata is volatile. The retained set lives in snapshots and events. Retry deadlines pick a fixed fair quantum, and recovery compacts a due replay suffix before starting another generation. |
| P-AUTO-1 | Consensus handles only opaque application payload digests. A successful application check gates validity and availability for producer and DA authority. `Automaton` is never used to fetch or verify V-QCs, nullifications, L-QCs, or leader blocks. | Automaton executor, chain planes, Core producer chains and DA | The producer context, parent, and payload completion, a generation-scoped offer of eligible runs, and then a durable signing reservation. |
| P-CUST-1 | After recovery, authority that depends on producer payloads stays private until `Automaton::verify(context, payload_digest)` confirms again that the payload and its parent are available. Multimmit adds no application supertrait or storage protocol, and consensus never fetches payloads. | Voter recovery phase, Core producer reachability | A sorted, bounded set of payload requirements derived from retained reachability. Each must verify `true` before dependent work is released. |
| P-PIPE-1 | Producer and DA choices that carry authority form a contiguous run of at most the chain's pipeline window (`d`, or one when `d = 0`) above the certified anchor, and each chain's proposals and votes stay within its own `d` and `e`. Speculative verification may finish out of order. Producer ancestry uses canonical header identities, while `Automaton` sees the separate opaque body commitment. | Core producer chains and DA | The header chain, the custody result, the producer or DA reservation, and certificate advancement. |
| P-DA-1 | Correct validators DA-vote once per `(chain, height)` along a contiguous held path. Certificates use one canonical transcript of exactly the DA quorum (`n - 2f`, or `n - f` when certificates bind) and advance monotonically. | Core DA, DA recovery task | DA choice, share, and certificate events. |
| P-TIPS-1 | `Tips(V-QC)` uses every designated vote in a V-QC of `n - f` to `n` messages: it drops `f` and carries branches with `2f + 1` support. Finalized tips drop `3f` and need full extension support. Pool settledness uses the branch-specific rule in `STATE_MACHINE.md`. | Tip algebra, Core finality | Pure tally algebra and the finalized floor event. |
| P-COMMIT-1 | Every non-genesis leader block carries the correct tip commitment, which authenticates the full safe-tip history. | Tip history type, Core view | The leader's signing reservation includes the commitment. |
| P-LEAD-1 | `n - f` votes from a retained pool finalize a leader. An L-QC is portable evidence and does not gate local finality. Finality only moves forward within the bounded lifetime of a pool. | Core finality | The frozen sticky pool, the finalized floor event, and an optional L-QC event. |
| P-CONS-1 | Leaders finalized at correct replicas form one authenticated chain of parent V-QCs, and repeated reports of the same finality evidence agree. Compatible finalized tips feed one prefix-compatible marshal ordering. Consensus keeps no dense log of its own. | Core view and finality, with marshal's order at the activity boundary | The finality fact and parent V-QC identity, the authenticated L-QC and history chain, and the ordered frontier. |
| P-VIEW-1 | Vote, novote, and nullify choices exclude each other. A valid V-QC or nullification exits exactly one view. Nullifying after voting follows the non-support rule. A receiver accepts any valid earlier parent that comes with the complete nullification gap, even when it knows a higher V-QC. | Core view and durable stance slots | Stance and signing events, the authenticated exit event, and the retained proof. |
| P-VQC-1 | A V-QC accounts for `n - f` to `n` distinct participants in disjoint, complete, attributed categories, with at least `2f + 1` votes for one proposal. Only the first new V-QC for a view is forwarded on its own. A proposal carries its selected parent unless that same certificate was already forwarded. | Core view and publication, V-QC tally | The immutable aggregation transcript, the fact that a view's first V-QC was forwarded, and the proposal's parent identity. |
| P-RES-1 | The resolver fetches only authenticated view-exit evidence and DA certificates. Demand is level triggered, and a covering L-QC re-anchors agreement without producer history. Exits may retire at the bounded retention floor. A node asks for a DA certificate on a chain with `d = 0` and `e = 0` only while the proposal anchor places the chain above every certificate it holds, and peers serve their newest durable certificate, so a node that lost a certificate before GST, and that peers no longer send, still recovers it. Catching up assumes at most `f` unavailable or Byzantine participants. | Core resolution, `ResolverCommand` capabilities, resolver actor | A retained proof, a held or durable certificate, or the finality floor satisfies demand. Retry state is volatile. |
| P-ASYNC-1 | Only a completion that matches a live request can change state or capacity. Completion order affects latency only: future exit proofs and producer-chain work may finish out of view or height order, and recovery keeps each live obligation without adding a second capacity contract. | Core capability identities, collaborator permits | Generation, job, request, subject, and transcript identities. The resulting event is the witness. |
| P-SNAP-1 | Only Core takes snapshots, and only of acknowledged state. Pruning never removes the only durable copy of a later event, and continuous load that produces authority cannot starve the snapshot cut. | Core `Snapshot`, journal owner | A checkpoint fence drains the staged prefix, the cut is taken at the acknowledged cursor, and every record above the cut is kept. |
| P-LIVE-1 | A stalled or faulty producer delays only its own chain. View and leader progress and the other producer chains stay live, assuming every correct producer block eventually verifies `true` with durable custody at every correct validator. Each chain bounds its own DA duties, so a chain whose certificates are late holds back only its own DA signing. | Core per-chain worklists, per-chain DA duty families, and discardable scheduler | No extra durable witness. Healthy chains keep advancing certificates, finality, and view exits. |
| P-RET-1 | One retirement pass bounds history without deleting a live dependency, proof, job, reservation, or publication. | Core retention | Reachability from the current floors and live tables. Snapshots contain the retained set. |
| P-BOUND-1 | Consensus exposes agreement facts only. It owns no bodies, no dense order or delivery state, and no application acknowledgement cursor. Reporter feedback carries no authority. | Engine API, Core snapshots, sparse inspection and activity | Their absence from consensus lifecycle types, durable codecs, snapshots, and normalized diagnostics. |
| P-MATTACH-1 | Consensus reports every L-QC it verifies as idempotent, best-effort `Activity::Proven` with the finality the certificate proves and the history records its placement fixed since the previous report, placement runs as fetch hints, and each DA certificate once its record is durable, plus every chain's newest record at start. Reporter feedback never gates progress or creates a durable event. Marshal's feed never blocks consensus: hints and older proofs may be dropped, records never are. Records missing from the feed are walked back from peers by the commitment an L-QC authenticates. A lost certificate report only delays reclaiming bodies. | Core activity drain and placement record queue, voter Reporter executor, marshal feed | The Proofs store in marshal, downstream of the accepted activity. |
| P-MSTORE-1 | Marshal's owner is the only mutator of its three stores: Blocks (custody and bulk segmented logs over one exact-reference index), Proofs (immutable L-QCs, records and cut entries), and Meta (one record). Every mutation is a job; a failed job stops marshal. A position is durable once a cut covering it completes. Prunes and floor installs make Meta durable (new base and retention) before deleting anything; at open, parts not connected to the base and blocks below retention are dropped. A segment is removed only when no retained row and no reader needs it. | Marshal owner and stores | The Blocks, Proofs and Meta logs and their manifests. |
| P-MRES-1 | Marshal fetches and serves only exact keys: a block and up to `len - 1` ancestors from an exact head, records backward from an exact commitment, a proof at or after a history, and an L-QC by identifier. Responses are size-bounded, decoded under protocol limits, and authenticated against the key on the resolver's task: blocks by head, parent links and body commitment, records by commitment chain, proofs by record commitment then certificate verification, L-QCs by the digest of the bytes. Serving answers only from held parts through snapshot readers off the owner, and never fetches. Subscriptions never start network work. | Marshal bridge, owner and `commonware-resolver` | The per-request key; the Proofs and Blocks stores are the durable witness. |
| P-MSYNC-1 | Marshal's order comes only from durable proofs: the openings of the connected records from the acknowledged cut to the strongest durable L-QC's leader history, oldest first, then that L-QC's final sweep. Following the paper's proposal-first variant, each sweep is offset-major in two passes and stops at a positional shortfall or an unsettled chain. A later or stronger target abandons the sweep in progress, and the openings that follow skip heights already emitted. Each position is resolved off its authenticated tip's own path, so an anchor jump extends the order. Positions and cuts are symbolic, with no digests. Output indices are canonical, the sum of the emitted heights. | Marshal order, `order` module | The acknowledged cut in Meta and the stored records and L-QCs. |
| P-MDEL-1 | Reporter receives the complete transaction block at the next `OutputIndex` once its proof, identity path and body are durable and the acknowledgement window has room. Several `Exact` acknowledgements may be in flight; the acknowledged cut advances only over their contiguous prefix, one Meta write at a time. A crash may repeat outputs after the durable acknowledgement and cannot skip any. | Marshal delivery | The acknowledged cut in Meta. |
| P-MBOUND-1 | Marshal's working set does not grow with catch-up distance beyond its stated bounds: the order window (four positions per chain per pipeline slot), hot bodies, fetch reservations, served requests, and the feed lane (proofs and placement runs bounded, records bounded by bytes with a fatal overflow) are configured. Consensus queues at most 1024 placed records for the next proof report. The block and proof indexes grow with what the application retains (about 130 bytes per held block) and shrink as it prunes; records above the delivered cut stay in memory until delivery passes them. | Marshal config, owner, feed lane; core placement | The configured limits and the retention floors in Meta. |

Marshal stores portable proofs and complete transaction blocks, applies the deterministic
proposal-first ordering from Section 6 of the paper from durable proofs only, runs the settled and
unsettled sweeps, and owns the durable acknowledged cut. Application bodies stay
opaque, so duplicate transactions inside bodies are the application's concern. Consensus and marshal
meet only at the best-effort activity stream described by P-MATTACH-1.

## Specification crosswalk

Each row maps a part of the paper to the properties that implement it. The status says whether the
mapping is direct, an optional feature from Section 6, a local refinement, or an assumption the
environment must supply.

| Specification item | Properties | Status |
|---|---|---|
| Model and cryptographic assumptions | P-ADM-1, P-SIGN-1, P-ASYNC-1 | Direct. Profiles require `n >= 5f + 1`, and verification binds the committee identity, the context, and the signed subject. Liveness also assumes at most `f` faulty or unavailable participants. |
| Section 4.1, transaction blocks and Algorithm 1 | P-AUTO-1, P-PIPE-1, P-DA-1, P-LIVE-1 | Direct, plus an application gate. Headers bind the chain, height, parent, and payload commitment. Core enforces one DA vote per height, contiguous ancestry, each chain's pipeline window, and certification by the DA quorum. `Automaton::verify` adds a local validity and custody check before any authority. |
| Section 4.2, leader blocks, proposals, and Algorithm 2 | P-COMMIT-1, P-PIPE-1, P-SIGN-1, P-VIEW-1, P-VQC-1 | Direct, except for what the leader proposes. The scheduled leader anchors on a greatest-view V-QC and proposes each chain at its certified base, and the DA-voted blocks that the paper's `ProposeChains` would include travel as vote extensions instead. Validity still admits up to `d` blocks per chain, and receivers validate the referenced V-QC and the nullification gap. Vote, novote, and nullify choices occupy durable exclusive slots. |
| Section 4.2, V-QCs and L-QCs | P-VQC-1, P-LEAD-1 | Direct. A V-QC holds complete, disjoint, attributed view messages with at least `2f + 1` votes for its designated proposal. An L-QC or retained pool has at least `n - f` distinct votes. |
| Section 4.2, `Tips` and `Tips*` | P-DA-1, P-TIPS-1, P-LEAD-1 | Direct for the rank and carry thresholds. Safe tips use rank `f + 1` and support `2f + 1`. Finalized tips use rank `3f + 1` and support `n - f` above a fully supported proposal. |
| Section 4.2, pool settledness | P-TIPS-1, P-LEAD-1 | Local refinement. Core uses `max_child_support + (n - \|P\|) <= f` in place of the aggregate `beta + (n - \|P\|) <= f`. [Leader finality](https://github.com/commonwarexyz/monorepo/blob/main/consensus/src/multimmit/docs/STATE_MACHINE.md#leader-finality) gives the branch-specific argument, and differential algebra tests cover competing branches. |
| Section 4.2, `Ord` and `Emit` | P-CONS-1, P-MATTACH-1, P-MSYNC-1, P-MDEL-1 | Implemented by marshal. Consensus reports authenticated finality facts. Marshal resolves history and bodies, builds a deterministic prefix, persists it, and owns delivery acknowledgement. As in `Horiz`, blocks are read off each target tip's own path, including after an anchor jumps to a branch incompatible with the previous tip. |
| Lemma 1, certified blocks are compatible | P-DA-1, P-PIPE-1 | Direct: one durable DA choice per chain and height, contiguous ancestry, exact certificate transcripts, and monotone certified anchors. |
| Lemmas 2-5: one vote per view, vote-novote exclusivity, designation, no nullification | P-SIGN-1, P-VIEW-1, P-VQC-1 | Direct: durable stance slots and exact quorum validation. Structured-artifact tests mutate the signer, category, context, and designation independently. |
| Lemma 6, the leader chain | P-CONS-1, P-LEAD-1, P-VIEW-1 | Direct: exact parent V-QC identity and proposal validation. Twins joins finality reports with digest-addressed wire evidence and requires complete, compatible ancestry for finalized leaders. |
| Lemma 7, safe extension | P-DA-1, P-TIPS-1, P-LEAD-1 | Direct for tip dominance. The local settledness rule needs its own argument, covered under pool settledness above. |
| Lemma 8, emission is a prefix | P-CONS-1, P-TIPS-1, P-MSYNC-1 | Direct for the chosen deterministic sweep. The algebra campaign compares incremental final tips with a materialized reference, and the marshal campaign compares incremental ordering and replay with an explicit enumeration. |
| Theorem 1, consistency | P-CONS-1, P-LEAD-1, P-MSYNC-1, P-MDEL-1 | End to end. Twins checks that finalized leaders and exact finality evidence are compatible, and marshal checks prefix-compatible ordering and durable delivery. These finite campaigns catch regressions and do not prove the theorem. |
| Lemmas 9-10 and Corollary 1, view synchronisation and exit | P-PUB-1, P-RES-1, P-VIEW-1, P-VQC-1, P-LIVE-1 | Direct under partial synchrony. Forwarding the first new V-QC or nullification, together with the resolver, supplies authenticated exit evidence. Timers and the non-support rule drive nullification, and exits advance one view at a time. |
| Lemma 11, correct-leader views | P-PIPE-1, P-PUB-1, P-VIEW-1, P-VQC-1, P-LEAD-1, P-LIVE-1 | Direct under partial synchrony. After a fair suffix, proposal construction, anchor dissemination, both voting routes, and pool finality follow the correct-leader path. |
| Theorem 2, liveness | P-AUTO-1, P-CUST-1, P-PIPE-1, P-DA-1, P-VIEW-1, P-LEAD-1, P-LIVE-1, P-MRES-1, P-MSYNC-1, P-MDEL-1 | Depends on the environment. It needs message delivery after GST, working runtime and storage, repeated views, eventual production and DA certification, application custody at correct validators, correct-leader finality, and retrieval from a correct holder. |
| Lemma 12, availability | P-AUTO-1, P-CUST-1, P-DA-1, P-TIPS-1, P-LEAD-1, P-MRES-1 | Direct, with a retrieval path added by the implementation. DA custody and certification establish holders, safe and final tip extraction decides which holder bound applies, and marshal retrieves authenticated blocks. Requiring every correct validator to verify `true` before its own DA vote is a stronger local gate than the lemma needs. |
| Lemma 13, membership finality | P-DA-1, P-TIPS-1, P-LEAD-1 | Direct threshold mapping. The guarantee follows from signed vote evidence, and consensus exposes no separate cursor for it. |
| Theorem 3 and Corollary 2, block inclusion and in-view finality | P-DA-1, P-TIPS-1, P-LEAD-1, P-LIVE-1, P-MSYNC-1 | Holds under the theorem's DA-vote and extension-depth hypotheses. The censorship scenario supplies them, and marshal realizes eventual placement. |
| Corollary 3, chain-local finality | P-CONS-1, P-TIPS-1, P-LEAD-1, P-BOUND-1, P-MATTACH-1, P-MSYNC-1 | Leader-chain compatibility and safe extension keep the finalized chain prefix across later views. Consensus authenticates that history, marshal resolves and orders it, and consensus exposes no dense delivery cursor. |
| Accountability | P-ACCT-1, P-SIGN-1 | Core recognizes the paper's self-contained pairs of conflicting signed messages and asks the network layer to quarantine the signer. Certificate transcripts count because validation authenticates each attributed message. DA shares are checked individually only when two distinct headers could form a proof. Junk-entry challenges, omission, slashing, and reputation are outside consensus. |
| Theorem 4, exact extension threshold | P-TIPS-1 | The implementation uses the Section 4 threshold `n - f`. The theorem shows that threshold is optimal at `n = 5f + 1` and allows a lower safe threshold for larger committees. The generalized threshold is not implemented. |
| Section 6, backup proposals | P-VIEW-1, P-LEAD-1 | Not implemented. Each view has one scheduled leader proposal, and timeout and nullification handle a crashed leader. |
| Section 6, skipping leaders that appear crashed | P-VIEW-1, P-LIVE-1 | Implemented through `Tuning::skip_timeout`, which defaults to five view timeouts. On entering a view, a validator times out a remote leader early if it has received nothing from that leader within the window while a view quorum, counting itself, was active. The local leader is never skipped. |
| Section 6, ordering by reputation | P-CONS-1, P-MSYNC-1 | Not implemented. Marshal keeps the fixed horizontal chain order, with no blame set or per-view shuffle. |
| Section 6, the proposal before the extensions | P-CONS-1, P-MSYNC-1 | Implemented. Marshal's two-pass sweep visits positions up to each proposed tip first and the extensions second, each pass in horizontal order, so a halt among extension votes defers only extension content. |
| Section 6, anchor choice and larger V-QCs | P-TIPS-1, P-VQC-1 | Implemented. A leader may pick another greatest-view V-QC if it disseminates that anchor itself. V-QCs may hold `n - f` to `n` messages, and tip extraction uses every retained designated vote, breaking ties between branches deterministically. |
| Section 6, tip commitments | P-COMMIT-1, P-MATTACH-1 | Implemented. Each leader block commits recursively to the safe-tip history, so marshal can authenticate history openings without replaying old V-QCs. |
| Section 6, one signature scheme | P-DA-1, P-VIEW-1 | Not implemented. Each key role is its own scheme, chosen by the deployment's suite; the default suite uses threshold BLS signatures for DA certificates and nullifications and BLS multi-signatures for votes, novotes, blocks, and V-QC/L-QC transcripts. |
| Section 6, batch verification and transport | P-ADM-1, P-OBS-1, P-ASYNC-1 | Batch verification is implemented, with optimistic aggregate checks that isolate invalid artifacts. Content-addressed vote transport and advertise-and-pull forwarding are not implemented. |
