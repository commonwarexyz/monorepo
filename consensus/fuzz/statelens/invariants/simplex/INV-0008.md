## Statement
If the replica receives a notarize, nullify or finalize vote from a network sender whose
committee index differs from the vote's signer index, or from a sender outside the committee,
then the replica shall not count that vote toward any certificate.

## Rationale
To deduplicate per signer, the replica must tie each vote to exactly one participant. With
the sender bound to the signer, one participant's vote can reach vote collection only over that
participant's own authenticated connection, where per-signer dedup applies. If the replica
also counted votes relayed or injected by other senders, the same signer's vote could arrive
through several senders. That is the multi-source delivery behind issue #2070, which reached
assembly as a repeated signer. It would also let one Byzantine peer attribute collected votes
to other participants, hiding which peer injected them. Rejecting mismatched votes keeps "one
signer index, one sender" true on the vote path, and INV-0002, INV-0003 and INV-0006 rely on it.

## Evidence
Issue #2070: two twin validators sharing one key sent the same signer-3 notarize vote for
view 5. Another replica collected [signer 3, signer 3, signer 4] and panicked during
notarization assembly with "duplicate signer index: 3". The reporter noted that "a malicious
validator can send two votes and crash all the nodes". PR #2102 (merge commit
6ca07aba2fee6a37c166885abc94724c77f0b679) closed the issue by requiring each committee
identity to map to exactly one consensus key ("We assume in some places (like consensus) that
there is a unique value ... associated with each registered key"). That mapping makes a
signer index correspond to exactly one network sender.

## Preconditions / assumptions
The committee satisfies INV-0004 (unique identity and consensus keys). The sender is the
authenticated peer identity reported by the network layer. Certificates carry other
participants' votes legitimately and are out of scope here; see INV-0007. The replica's own
locally constructed votes are not network votes.

## Observation hints
`Round::add_network` in `consensus/src/simplex/actors/batcher/round.rs:225` maps the sender to
an index and rejects `index != vote.signer()` (lines 236, 266, 300) before the vote reaches
`VoteTracker` or the verifier. Votes arrive from the vote channel in
`actors/batcher/actor.rs:601-635`. An assertion can check that every vote passed to
`accept_vote(.., false)` has a signer equal to the sender's committee index.
