## Statement
The replica shall not participate in consensus for an epoch whose committee contains two
participants with the same identity key or two participants with the same consensus key.

## Rationale
Simplex maps each participant to one index, and the replica attributes each vote to the
participant at the signer index. If two indices share a consensus key, one private key can sign
as either index, so a single Byzantine key holder counts as two participants toward a quorum. If
two indices share an identity key, the replica cannot tell which index a network sender is, so
the check that a vote's sender matches its signer no longer identifies one participant. Both cases
break the assumption that at most f participants are faulty.

## Evidence
Issue #2070 was found by running two validators with the same key in one committee (Twins). The
replica received the same vote for one signer index from both twins, passed both to certificate
assembly, and panicked. PR #2102 ("Introduce BiMap", merge commit
6ca07aba2fee6a37c166885abc94724c77f0b679) fixed the issue by construction. Its description:
"We assume in some places (like consensus) that there is a unique value (i.e. consensus public
key) associated with each registered key." The PR replaced the committee's identity-to-consensus
key map with a bijective map and the identity list with a set that rejects duplicates.

## Preconditions / assumptions
Applies to every committee the replica loads, including committees for later epochs after
reconfiguration.

## Observation hints
The signing schemes take participants as `ordered::Set` (identity keys) and `ordered::BiMap`
(identity key to consensus key). Building them from duplicates fails in `try_collect` or
`try_from_iter`. Check the scheme's `participants()` and the consensus keys whenever a scheme
is built for an epoch.
