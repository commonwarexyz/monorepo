## Statement
The replica shall not sign a nullify-vote for a view `v` unless, in view `v`, at least one of the
following has occurred: 
- verification of the leader's proposal (the container) failed;
- certification of the notarized proposal failed; 
- the leader timeout `t_l` or the advance timeout `t_a` fired, including their immediate expiry when the leader has been inactive; 
- the stall timeout fired;
- the replica, as leader, failed to build its proposal (local proposal failure);
- local verification of the proposal failed; 
- the replica received the current leader's `nullify(v)` vote for view `v`;
- when the retry interval `t_r` elapses while the replica is still in view `v`, it may sign its nullify vote for `v` again,
  once one of these triggers has already occurred.

## Rationale
A nullify vote supports skipping a view, and a quorum of them lets later leaders skip it. The
protocol's forced-inclusion property rests on honest replicas nullifying only on a trigger: a
nullification covering a view needs nullify votes from at least `f+1` honest replicas, so if no
trigger fires, no nullification can form, and a notarized proposal of that view must appear in the
chain. A replica that votes nullify without a trigger helps Byzantine replicas form a nullification
around a view that was never stalled, which lets a later leader fork around a notarized proposal
(tail forking). Tying every nullify vote to a trigger also makes timeouts and failures, not
arbitrary choices, the only way a view is skipped.

## Evidence
Human-authored from the module documentation of `consensus/src/simplex/mod.rs`. "If verification
of `c` fails, immediately broadcast `nullify(v)`" (line 46). Certification: "On failure: treat as
immediate timeout expiry and broadcast `nullify(v)`" (line 55). "Upon `t_l` or `t_a` firing:
Broadcast `nullify(v)`; Every retry interval `t_r` after `nullify(v)` broadcast that we are still in
view `v`: Rebroadcast `nullify(v)`" (lines 65-72). Deviations: "Treat local proposal failure as
immediate timeout expiry", "Treat local verification failure as immediate timeout expiry",
"Consider the current leader's `nullify(v)` as immediate timeout expiry" (lines 124-126), the skip
timeout for an inactive leader (lines 119-121), and the stall timeout (lines 137-140). The protocol
properties section summarizes: "An honest participant only broadcasts `nullify` on a nullify
trigger: an expired timeout (`t_l`, `t_a`, or the stall timeout) or an event treated as immediate
timeout expiry (proposal build failure, verification failure, certification failure, the leader's
own `nullify`, or leader inactivity)" (lines 161-165).

## Preconditions / assumptions
The triggers concern view v itself: a timeout of view v, a failure about view v's proposal, or a
nullify vote for view v from the leader of view v. The list is the complete set of nullify
triggers given in lines 161-165, with the retry interval t_r allowed only for signing an existing
nullify vote again. A nullify vote replayed from the journal after a restart is the vote the
replica signed before the restart, not a new one. With stable leaders (term length above 1), the
stall timeout is the one that tracks the oldest unfinalized view of the current term.

## Observation hints
Nullify votes are signed through `State::construct_nullify(view, reason)` in
`consensus/src/simplex/actors/voter/state.rs`, where `reason` is a `TimeoutReason`
(`consensus/src/simplex/metrics.rs`): `InvalidProposal` (the application's verify returned false),
`FailedCertification`, `LeaderTimeout` (t_l), `CertificationTimeout` (t_a), `StallTimeout`,
`Inactivity`, `MissingProposal` (the propose request failed, see `Actor::process_proposed`),
`IgnoredProposal` (the verify request failed, see `Actor::process_verified`), `LeaderNullify`, and
`Retry` (t_r). Triggers are raised through `State::trigger_timeout`, `State::verification_failed`
and the `Round` deadlines in `actors/voter/round.rs`. The reason label is the implementation's own
claim, so a check should record, per view, the evidence for each trigger (the deadline that passed,
the failed verification or certification result, the leader's nullify vote) and assert at each
nullify signature that the view has one.
