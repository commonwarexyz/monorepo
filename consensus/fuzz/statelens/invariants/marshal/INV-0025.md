---
id: INV-0025
title: Inline parent re-proposals are restricted to the current epoch boundary
source_kind: comment
source_ref: consensus/src/marshal/standard/validation.rs:62
scope: [replica, standard, application]
---

## Statement
When accepting a proposal whose digest equals its declared parent's digest in inline mode,
the replica shall have obtained that block, established that its height is the last height of
the proposal's epoch, and completed durable storage of the block before returning a positive
verification result.

## Rationale
A boundary re-proposal preserves the existing block instead of extending beyond the epoch.
It deliberately bypasses the ordinary parent/height and application checks, which would otherwise
treat the block as its own parent. Restricting this bypass to a confirmed boundary block prevents
ordinary blocks from being accepted through the exception.

## Evidence
`standard/inline.rs:11` describes re-proposing the epoch's last block. The shared
`precheck_epoch_and_reproposal` in `standard/validation.rs:70` first checks epoch membership,
recognizes equality with the declared parent, rejects a non-boundary height, and awaits durable
storage before returning a positive result. `Inline::verify` returns that precheck result without
calling the application again for a valid boundary re-proposal.

## Preconditions / assumptions
The replica is honest and the consensus context's parent has the required consensus evidence.
The original view's certification establishes the boundary block's validity. A verification
rejection under a header declaring the block as its own parent does not by itself prove that a
notarization for the same digest under another header is invalid; inline certification remains
governed by INV-0024.

## Observation hints
Observe `Inline::verify`, `precheck_epoch_and_reproposal`, and
`is_valid_reproposal_at_verify` in `consensus/src/marshal/application/validation.rs`. Compare
against the last height of the verification context's epoch, not merely a boundary in any epoch.
This exception requires durability before verify succeeds even though ordinary inline verification
can finish before storage does.
