id: INV-0021
title: Deferred certification requires a valid and durable complete block
source_kind: comment
source_ref: consensus/src/marshal/standard/deferred.rs:265
scope: [replica, standard, application]

## Statement
When positively certifying an externally proposed new block in deferred mode, the replica shall
have verified that the block extends the parent named by its verified context at exactly the next
height, obtained a positive application-verification result for that block and context, and
completed durable storage of the block.

## Rationale
A deferred notarization establishes availability and context agreement, not application validity.
Certification is the barrier that prevents an invalid or non-durable candidate from authorizing
a finalize vote. Persisting a candidate early must not bypass that barrier.

## Evidence
`standard/deferred.rs:265` explicitly permits storage before validation but requires both a
positive application verdict and durability before the certification gate resolves positively.
`standard/validation.rs:33` checks the child's parent digest, the expected parent's digest, and
contiguous heights. `Deferred::certify_from_embedded_context` uses the same deferred verification
when no applicable local verification task survives.

## Preconditions / assumptions
The replica is honest and certification is requested for a valid notarization. A new block excludes
an epoch-boundary re-proposal, whose original certification settles validity; locally built blocks
use the application's proposal contract instead of another application-verification call. During
recovery, the block's embedded context supplies the verified context, justified by the honest
notarizers' context checks. Missing data, cancellation, or runtime shutdown need not yield a verdict;
an actual storage failure is fatal and is not a live rejection of the block.

## Observation hints
Follow `Deferred::deferred_verify`, `certify_from_existing_task`, and
`certify_from_embedded_context` in `consensus/src/marshal/standard/deferred.rs`, and `resolve` in
`consensus/src/marshal/application/gates.rs`. Track the block, context, application verdict, and
completed sync separately. The verified/notarized caches may contain app-invalid candidates, so
cache membership does not prove this invariant's validity condition.
