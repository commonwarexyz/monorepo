## Statement
When accepting a new proposal for notarization in deferred mode, the replica shall already hold
the block matching the proposed digest, with a height in the proposal's epoch and an embedded
context equal to the consensus context being verified.

## Rationale
Deferred mode overlaps application verification with notarization, but does not make availability
or context checks speculative. Honest notarizers establish the context that replicas which missed
the proposal will later use when certifying from the block alone.

## Evidence
`standard/deferred.rs:17` requires block availability and embedded-context agreement before a
notarize vote. `Deferred::verify` awaits the block, applies the shared epoch precheck, and rejects
a context mismatch before returning a positive verification result. The mismatch requests
certification recovery instead of supplying a definitive negative certification verdict.

## Preconditions / assumptions
This concerns an honest replica's proposal-verification result. A new proposal has a digest
different from its declared parent. A valid re-proposal of the current epoch's last block retains
its original embedded context and is excluded from the context-equality requirement. Application
verification and durable storage need not have completed for an ordinary positive verify result.

## Observation hints
Observe `Deferred::verify` in `consensus/src/marshal/standard/deferred.rs`, especially the block
subscription, `precheck_epoch_and_reproposal`, context comparison, and positive response.
`consensus/src/marshal/standard/validation.rs:70` implements the shared epoch precheck. A cache
insertion alone is not a positive verification result.
